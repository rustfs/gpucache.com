RustFS GPUCache · G3.5 In development

KV Cache at the G3.5 tier, running on a DPU.

GPUCache is a DPU-based GDS KVCache. It stores KV Cache that does not fit in GPU memory on shared NVMe flash managed by a DPU, and fills it back to the GPU when needed, so context that has already been computed does not have to be computed again.

Written in Rust · Apache 2.0 · BlueField-3 support in development

Follow progress on GitHub View the architecture

Problem

When context is evicted, the GPU has to recompute it.

Long context, multi-turn conversation, and agents make the KV Cache grow until GPU memory cannot hold it. The next time evicted KV is needed, it has to be prefilled again: the GPU spends cycles on work it has already done, and the first token waits longer.

Each existing tier has a limit. Host memory is finite. A node-local SSD serves one machine and is hard to share across nodes. Shared storage is built for durability and capacity, and it is not on the inference hot path.

Approach

Between G3 and G4, add a shared KV Cache tier.

GPUCache is a hot tier for KV Cache. A DPU manages shared NVMe flash for the whole GPU cluster.

  1. 01

    Built on a DPU In development

    The KV engine runs on the Arm cores of the DPU and manages flash directly. The storage side does not need an x86 storage host. BlueField-3 support is in development.

  2. 02

    GDS data path In development

    The target path runs from GPU memory through the DPU to NVMe flash, so KV data is not forwarded by the host CPU. The first stage opens the path through host memory.

  3. 03

    Hot tier only. A loss is a miss.

    GPUCache does not provide durability. A node failure or lost data is a clean miss. The inference framework recomputes, writes the result back, and the next use can hit. Data that must be kept goes to RustFS at G4.

Not a fit

  • Data that must be stored durably. G3.5 is a cache. Durable data belongs on RustFS at G4.
  • Checkpoint storage for training. That is work for G4.
  • A production deployment today. V1 is still in development.

Architecture

GPU, DPU, and flash, each with its own job.

GPUCache places the hot path for KV data between the NIC, the DPU, and the SSDs. The diagram below is the design target. Every component is in development.

  1. GPU memory / host memory
  2. RDMA / RoCEv2
  3. DPURust KV engine
  4. SPDK
  5. NVMe flash

In development

  1. 01

    Rust KV engine In development

    A storage engine for KV Cache, written in Rust, running on the Arm cores of the DPU.

  2. 02

    RDMA / RoCEv2 transport In development

    Compute nodes talk to G3.5 over RDMA.

  3. 03

    SPDK flash management In development

    SPDK on the DPU accesses NVMe SSDs directly.

  4. 04

    NVIDIA DOCA and Arm cross-compilation In development

    Build and run on BlueField-3.

  5. 05

    Inference framework integration In development

    Planned integration with the KV Cache interfaces of frameworks such as vLLM and TensorRT-LLM, managed at PagedAttention block granularity.

The data path advances in three stages: through host memory, then a staging path, then GDS direct. Only a combination that has been verified is labeled as supporting GDS direct. Architecture notes

How to read this roadmap

With RustFS

G3.5 holds what is hot. G4 keeps what must last.

Learn about RustFS

GPUCache is built by the RustFS team. The two have a clear split in the storage hierarchy. GPUCache is the G3.5 hot tier, close to the GPU and meant for reuse. RustFS is the G4 capacity tier, an S3-compatible distributed object store written in Rust, responsible for keeping models, datasets, session history, and inference artifacts.

A lost hot tier can be recomputed. Data in the capacity tier must not be lost. Keeping the two jobs separate makes each one simpler.
