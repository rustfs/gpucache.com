Architecture

GPUCache places the hot path for KV data between the NIC, the DPU, and the SSDs. What follows is the design target.

In development

BlueField-3 support, the DPU and GDS direct path, and integration with vLLM and TensorRT-LLM are in development.

What is on the main branch

The main branch contains the CPU and TCP contract: V1 A/B/C, a V2 slice (TCP, a shard-local directory, and a mock cold path), and V3 stubs (a DPU feature gate and production-hardening hooks). The runnable path is that CPU contract. BlueField-3, GDS, the DPU hardware path, and real RDMA or NIXL performance are in development and marked NOT_RUN_HARDWARE. Soft-RoCE is a functional smoke only, not a performance number.

There is no erasure coding and no hot-tier durability replica. A G3.5 miss or a lost node is a clean miss: recompute, then write back. RustFS at G4 keeps cold data. The diagram on this page remains the design target for the hardware path. Read the introduction and the usage manual.

Three roles

  • GPU Holds the KV used while generating, and asks for KV that has to come back.
  • DPU Runs the Rust KV engine and manages flash. BlueField-3 support is in development.
  • Flash Shared NVMe that holds KV the cluster can reuse.

Data path

The line below is the design target, not a path that is running today. The first stage to open is the one that goes through host memory.

  1. GPU memory / host memory
  2. RDMA / RoCEv2
  3. DPURust KV engine
  4. SPDK
  5. NVMe flash

In development

Three stages, all in development

  1. Host-memory path KV moves between host DRAM and the DPU and flash. This is the baseline the first stage has to open.
  2. Staging path Data in GPU memory is staged once, then handed to the DPU. This is a transitional form, and the staging has to be observable.
  3. GDS direct GPU memory reaches flash through the DPU, with no host staging. This is the target shape of GPUCache.

Public material can call a path GDS direct only after runtime evidence: the direct path was actually taken, there was no fallback and no silent staging, and the bytes and the checksums match at both ends. An interface or a device type is not that evidence.

Components

  1. 01

    Rust KV engine In development

    A storage engine for KV Cache, written in Rust, running on the Arm cores of the DPU.

  2. 02

    RDMA / RoCEv2 transport In development

    Compute nodes talk to G3.5 over RDMA.

  3. 03

    SPDK flash management In development

    SPDK on the DPU accesses NVMe SSDs directly.

  4. 04

    NVIDIA DOCA and Arm cross-compilation In development

    Build and run on BlueField-3.

  5. 05

    Inference framework integration In development

    Planned integration with the KV Cache interfaces of frameworks such as vLLM and TensorRT-LLM, managed at PagedAttention block granularity.

Where the CPU sits

The storage side does not need an x86 storage host, and the hot path for KV data is not forwarded by the host CPU. Compute nodes still keep a minimum of state: registered memory, submitted requests, and completion events.

What a loss means

GPUCache does not take on durability. When a G3.5 node fails or data is lost, the inference framework gets a miss, prefills again the way it already would, writes the result back to GPUCache, and the next use can hit.

Context and artifacts that have to be kept go to RustFS at G4. RustFS is the capacity tier. GPUCache is the hot tier.

Not a fit

  • Data that must be stored durably. G3.5 is a cache. Durable data belongs on RustFS at G4.
  • Checkpoint storage for training. That is work for G4.
  • A production deployment today. The CPU contract runs from source; the hardware path is in development, and this tree is not production-ready.
