Tiering

The names below are the usual ones for inference KV Cache tiering. GPUCache is G3.5. It is not another name for G4.

In development

Current implementation: CPU/TCP with host copies; persistent FileStore is a CPU reference backend. The DPU/NVMe/GDS layout in the table is a design target. Real RDMA, GDS and BlueField-3 remain NOT_RUN_HARDWARE. Cold tests use a mock; live RustFS integration is unqualified.

TierMediumScopeRole for KV CacheProduct
G1GPU HBMOne GPUHot KV used while generating—
G2Host DRAMOne nodeStaging and buffer for KV unloaded from HBM—
G3Node-local NVMe SSDOne nodeWarm KV for short-term reuse. Not shared across nodes.—
G3.5Shared NVMe flash managed by a DPU and reached over Ethernet or RDMAShared inside a GPU pod or clusterA hot tier of reusable KV Cache, brought back to G2 or G1 when needed. A loss is a miss; recompute, then write back.GPUCache (in development)
G4Shared network storage (object storage)Data-center scaleDurable cold data: models, datasets, session history, inference artifactsRustFS

The same stack, drawn out

  1. G1HBM
  2. G2DRAM
  3. G3NVMe
  4. G3.5GPUCache
  5. G4RustFS

G3.5 is the Signal block. It is easier to share than the node-local SSD at G3, and closer to the inference hot path than the shared store at G4.

The boundary between G3.5 and G4

GPUCache does not take on durability. When a G3.5 node fails or data is lost, the inference framework sees a miss, prefills again the way it already would, writes the result back to GPUCache, and the next use can hit.

Context and artifacts that have to be kept for a long time go to RustFS at G4. The hot tier can be recomputed. The capacity tier is where data must remain.
