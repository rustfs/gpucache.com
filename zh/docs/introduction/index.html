介绍手册

介绍手册

GPUCache 是 G3.5 共享 KV 热层。RustFS 是更冷的 G4 容量层。这棵树里现在能跑的是 CPU/TCP 契约。BlueField-3、GDS、DPU 硬件路径，以及真实的 RDMA/NIXL 性能，一律是「开发中」。

已实现开发中

V1 A/B/C 和 V2 的 CPU 切片已在主分支。V3 是 DPU 特性门和加固用的桩。硬件路径打印 NOT_RUN_HARDWARE。Soft-RoCE 只做功能冒烟，不是性能数字。

定位能跑什么架构G3.5 与 G4同一套协议

产品定位

GPUCache 是面向分离式推理的开放共享 KV Cache 层。按 NVIDIA CMX 的说法，这一层是 G3.5：放在 GPU HBM 前面，供同一租户、同一模型、同一布局的请求复用。RustFS 是 G4 容量后端。G4 不在 prefill 到 decode 的热路径上。

一个 KV block 是可重算的加速器状态。它不是用户 prompt 的唯一副本，也不是与模型无关的长期记忆。分词、注意力和调度仍由推理引擎负责。本仓库不替代这些工作。

未命中、超时、校验失败、版本不匹配或存储不可用，都回到引擎。引擎重算，并可以把 block 写回。错误的命中是故障。没有可安装的包，没有生产部署，也没有测过的集群规模。不要把这棵树写成 PB 级或生产就绪。

许可是 Apache 2.0。对外措辞以 主分支 README 和旁边的文档为准。

能跑的，和仍在开发中的

默认构建是 CPU 和 TCP。它不链接 DOCA、CUDA、RDMA、NIXL 或 SPDK。aarch64 构建仍是 CPU 构建，不是 BlueField 功能测试。特性 rdma-nixl 不链接 libnixl。特性 dpu-bf3 不链接设备。NixlTransport::open、open_doca、open_nvme_device 和 open_spdk 都会拒绝。

事项状态含义
V1 A/B/C CPU 契约已实现身份、协议、MemoryStore、TCP 服务、文件后端、LRU 准入、租户配额、模糊测试和故障测试。字节是合成的。真实的 vLLM KV 导出是 NOT_RUN_HARDWARE。
V2：TCP、分片目录、冷路径已实现TCP 是默认传输。注册是模拟缓冲池，不是网卡。一个进程是一个分片。G4 打包和回填对着 mock 跑。除非操作者设置 GPUCACHE_RUSTFS_*，否则在线 RustFS 是 NOT_RUN_HARDWARE。
V3：DPU 门和加固桩开发中CPU 侧的鉴权、重放、配额和冷操作钩子在树里。再平衡和滚动升级会拦住填充，不复制副本。设备没有链接。dpu-demo 打印 NOT_RUN_HARDWARE。
BlueField-3、GDS、DPU 硬件路径开发中始终是「开发中」。没有实现，没有部署，也不是测过的生产路径。
真实 RDMA / NIXL 性能开发中在线 RDMA 是 NOT_RUN_HARDWARE。不公布成对的 TTFT、TPOT 或 TCO。tco=TCO_UNKNOWN。go_gate=NOT_EVALUATED。TCP 不是 DPU 的对照基线。
Soft-RoCE仅冒烟Soft-RoCE 只做功能冒烟。它不是性能数字，本站也不公布这个数字。
引擎对接开发中路线尚未选定，原生 vLLM KV connector 或 LMCache 都还没定。没有加入第二个引擎。
纠删码和热层副本不在本产品中不会做。热层纠删码不能打开。丢失的热 block 是一次干净的未命中。

命令、成功横幅，以及每个演示的边界，写在 使用手册。

架构

首页上的图是 DPU 路径的设计目标。这棵树没有跑过那条路径。现在能跑的结构是：

engine (not in this tree; NOT_RUN_HARDWARE)
        |  CacheIdentity + batch API
        v
gpucache-transport    TCP, loopback by default
        v
FileStore             ordinary files in a directory you pass
        v
MemoryStore           in-process contract
gpucache-cold         optional G4 mock. Not on the TCP hot path.
gpucache-dpu          simulated queue. Not on the TCP hot path.
  • gpucache-core-types 放版本化的 CacheIdentity、带长度的逻辑键和物理键、block 生命周期、校验和、配额和错误。
  • gpucache-protocol 放批量消息、截止时间、租户认证上下文和线协议版本协商。
  • gpucache-storage 放 MemoryStore、FileStore 和 kv-block-xfer。FileStore 不格式化磁盘，也不打开设备节点。
  • gpucache-transport 是 TCP 正确性路径，外加模拟的注册缓冲池和分片本地目录。
  • gpucache-cold 打包清单，并可以通过 trait 做 Put、Head、RangeGet 和 Delete。传输层不依赖它。
  • gpucache-dpu 是 BlueField 特性槽。热路径不调用它。
  • gpucache-bench 只点名成对基线，并打印 NOT_RUN_HARDWARE。它不能编造时延数字。

只有身份兼容、且存储的校验和仍与字节一致的 COMMITTED block 才是命中。ABSENT、RESERVED、WRITING、EVICTING 和 QUARANTINED 都不可读。

ABSENT -> RESERVED -> WRITING -> COMMITTED -> EVICTING -> ABSENT
                 \-> QUARANTINED -> ABSENT

失败或超时的已注册区域进入 QUARANTINED。租约到期不会释放它。回收需要授权的排空证明，或一个更新的 epoch 把该区域隔离开。更长的哈希链可以在布局和其他影响字节的字段匹配时，对一整块更短的已提交 block 返回 PrefixHit。服务不会在 block 内部切片。同一条链上更短的 valid_length 是不兼容的未命中。

原始 prompt、token id 和媒体字节不是身份字段。调用方在存储之外对它们做哈希。相同的 token 不表示相同的字节：逻辑前缀键和物理字节键是两种编码。复用只发生在同一租户、同一模型、同一布局之内。重分片、量化或布局不匹配都是未命中。没有跨租户去重。

G3.5 与 G4

G3.5 的 GPUCache 是共享热层。G4 的 RustFS 是冷容量层。热层不修复丢失的 block。没有纠删码，热层也没有持久副本。丢失、损坏、写短、磁盘满、驱逐和检查失败，都是一次干净的未命中。引擎重算，并可以把 block 写回。

如果内存里已经提交、随后的落盘失败，这次提交会被放弃，request id 也会忘掉，这样重放就不能把没写上的字节报成成功。热共享前缀的额外副本如果将来加上，也只是时延提示。它不在这棵树里，也不会是持久性承诺。

冷数据的持久性是 RustFS 的工作。TCP 服务不调用冷 crate。超出预算的回填，或变慢、宕机的 RustFS，都不返回载荷。这个结果是重算，不是命中。这里对在线桶走 https:// 是 NOT_RUN_HARDWARE，因为没有链接 TLS 栈。除非操作者已经授权测试桶，否则不要设置 GPUCACHE_RUSTFS_*。

从单节点到分布式，协议相同

每条能跑的路径都用同一套批量 API：Lookup、Reserve/Put、Commit、Get、Release/Cancel 和 Invalidate。每个条目都带 request_id、epoch 和 deadline，适用时还带 generation、长度和校验和。

MemoryStore 是进程内、单线程的契约。TCP 服务提供同一套 API。分片 0 就是单节点情形，使用和其他分片相同的 ShardDirectory 方法。一个进程是一个分片。没有按 token 的中心目录，也没有按 block 的仲裁。成员变更会抬高 epoch，丢掉进行中的填充，并释放额度。同一次 single-flight 的加入者不会再占一份额度，目录也不会把载荷字节交给他们。

这棵树里，从单节点走向分布式热层，就只有这一步：同一套协议，同一套目录方法，仍然是一个进程一个分片。跨分片不是另一套线协议，也不是已经在跑的仲裁。客户端如果还在对已经停掉的监听端说话，会得到传输错误，必须重算。它不会留着一个过期的命中。
