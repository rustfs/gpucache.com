RUSTFS GPUCACHE · G3.5 开发中

G3.5 层的 KV Cache，跑在 DPU 上。

GPUCache 是基于 DPU 的 GDS KVCache。它把放不进 GPU 显存的 KV Cache 存到 DPU 管理的共享 NVMe 闪存上，需要时回填给 GPU，算过的上下文不用再算一遍。

Rust 编写 · Apache 2.0 开源 · BlueField-3 支持开发中

在 GitHub 关注进展 查看架构

问题

上下文被逐出，GPU 就得重算。

长上下文、多轮对话和 Agent 让 KV Cache 越来越大，GPU 显存很快就装不下。被逐出的 KV 再被用到时，只能重新做一遍预填充：GPU 算的是已经算过的东西，首 token 也要多等一会儿。

现有的几层各有局限。主机内存容量有限；节点本地 SSD 只服务一台机器，难以在节点之间共享；共享存储是为持久性和容量设计的，不在推理热路径上。

方案

在 G3 和 G4 之间，加一层共享的 KV Cache。

GPUCache 是一层专门放 KV Cache 的热层，由 DPU 管理共享 NVMe 闪存，供整个 GPU 集群使用。

  1. 01

    基于 DPU 开发中

    KV 引擎运行在 DPU 的 Arm 核上，直接管理闪存，存储侧不需要 x86 存储主机。BlueField-3 支持开发中。

  2. 02

    GDS 数据路径 开发中

    目标路径是 GPU 显存经 DPU 直达 NVMe 闪存，KV 数据不经过主机 CPU 转发。第一阶段先打通经主机内存的路径。

  3. 03

    只做热层，失败即 miss

    GPUCache 不承担持久性。节点故障或数据丢失时就是一次干净的 miss，推理框架重算后写回，下次即可命中。需要持久保存的数据交给 G4 的 RustFS。

不适合的场景

  • 需要持久保存的数据。G3.5 是缓存，持久数据放 G4 RustFS。
  • 训练场景的 checkpoint 存储。那是 G4 的工作。
  • 想现在就部署到生产环境。V1 还在开发中。

架构

GPU、DPU、闪存，各司其职。

GPUCache 把 KV 数据的热路径放在网卡、DPU 和 SSD 之间。下面是设计目标，所有组件均在开发中。

  1. GPU 显存 / 主机内存
  2. RDMA / RoCEv2
  3. DPURust KV 引擎
  4. SPDK
  5. NVMe 闪存

开发中

  1. 01

    Rust KV 引擎 开发中

    面向 KV Cache 的存储引擎，用 Rust 编写，运行在 DPU 的 Arm 核上。

  2. 02

    RDMA / RoCEv2 传输 开发中

    计算节点与 G3.5 之间走 RDMA 通信。

  3. 03

    SPDK 闪存管理 开发中

    在 DPU 上用 SPDK 直接访问 NVMe SSD。

  4. 04

    NVIDIA DOCA 与 Arm 交叉编译 开发中

    在 BlueField-3 上构建和运行。

  5. 05

    推理框架对接 开发中

    计划对接 vLLM、TensorRT-LLM 等推理框架的 KV Cache 接口（按 PagedAttention 的块粒度管理）。

数据路径分三级推进：经主机内存 → 暂存 → GDS 直通。只有经过验证的组合才会标为「支持 GDS 直通」。 架构说明

与 RUSTFS

G3.5 放热的，G4 存久的。

了解 RustFS

GPUCache 由 RustFS 团队打造。两者在存储分层里分工明确：GPUCache 是 G3.5 热层，追求离 GPU 近、可以复用；RustFS 是 G4 容量层，是用 Rust 编写的 S3 兼容分布式对象存储，负责模型、数据集、会话历史和推理产物的持久保存。

热层丢了可以重算，容量层的数据不能丢。两件事分开做，各自都更简单。
