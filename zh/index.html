GPUCache 位于 G3.5：比节点本地 SSD 更容易共享，比共享存储更靠近推理热路径。G4 由 RustFS 承担。

问题

上下文被逐出，GPU 就得重算。

长上下文、多轮对话和 Agent 让 KV Cache 越来越大，GPU 显存很快就装不下。被逐出的 KV 再被用到时，只能重新做一遍预填充：GPU 算的是已经算过的东西，首 token 也要多等一会儿。

现有的几层各有局限。主机内存容量有限；节点本地 SSD 只服务一台机器，难以在节点之间共享；共享存储是为持久性和容量设计的，不在推理热路径上。

方案

复用兼容块，未命中时重新计算。

BlueField-3、GDS 和真实 RDMA 仍在开发中，状态为 NOT_RUN_HARDWARE。当前路径包含主机拷贝，不宣称零拷贝或绕过 CPU。

  1. 01

    当前可运行的路径

    源码包含 CPU/TCP、内存和普通文件后端，无需 GPU 或 DPU。

  2. 02

    单节点与多分片

    有界路由、连接和 epoch fencing 支持由运维方管理的分片。

  3. 03

    故障意味着重新计算

    G3.5 不增加纠删码或持久性副本。传输完成状态未知时保持隔离，只有显式排空或更新的 fence 才能允许复用。冷数据持久性归 RustFS；这是缓存契约，不是灾备，也不是集群规模验证。

不适合的场景

  • 需要持久保存的数据。G3.5 是缓存，持久数据放 G4 RustFS。
  • 训练场景的 checkpoint 存储。那是 G4 的工作。
  • 尚未完成生产部署验证。

与 RUSTFS

G3.5 放热的，G4 存久的。

了解 RustFS

GPUCache 由 RustFS 团队打造。两者在存储分层里分工明确：GPUCache 是 G3.5 热层，追求离 GPU 近、可以复用；RustFS 是 G4 容量层，是用 Rust 编写的 S3 兼容分布式对象存储，负责模型、数据集、会话历史和推理产物的持久保存。

热层丢了可以重算，容量层的数据不能丢。两件事分开做，各自都更简单。

构建、测试并检查 CPU 契约。

主分支已包含可运行的 Rust 代码，实现基于 CPU/TCP 的 G3.5 共享 KV 缓存。先运行软件契约测试，无需 GPU 或 DPU。
